A private address like 192.168.1.50 doesn’t tell the other machine how to get there. NAT rewrites addresses and ports, and the router also decides what return traffic it accepts. WireGuard overviewNetBird connectivity

What WireGuard handles

A public key identifies the peer.

AllowedIPs ties that key to tunnel addresses.

  • Sending

    The destination address selects the peer.

  • Receiving

    The decrypted source address must match that peer’s AllowedIPs.

  • Transport

    Encrypted packets over UDP. No built-in TCP fallback.

Key distribution, address assignment, and NAT traversal live outside WireGuard.

NC State Linux Users’ Group · October 16, 2026
Speaker notes and sources

~2 min. WireGuard is deliberately small. You configure a private key locally and give it the public keys of the peers it should trust. AllowedIPs does two jobs. Outbound, the destination picks a peer. Inbound, WireGuard checks the decrypted source address against the authenticated peer’s allowed addresses. That’s cryptokey routing. The handshake uses Noise with Curve25519, and the data uses ChaCha20-Poly1305. There’s no cipher menu to negotiate. On Linux, the tunnel can run in the kernel or through wireguard-go in userspace. But WireGuard doesn’t distribute those keys, choose your overlay addresses, or discover a path through two NATs. That’s the work NetBird does around it.

How the peers connect

  1. 1. RegisterSign in. Get the network map.
  2. 2. Find a pathDiscover addresses. Test candidates.
  3. 3. ConnectSend encrypted traffic.
NC State Linux Users’ Group · October 16, 2026
Speaker notes and sources

~3 min. This is the whole sequence. First, each client generates its keypair locally and registers using sign-in or a setup key. Management receives the public key and sends back an overlay address, authorized peers, and policy. Advance once. Each client asks STUN what public address and port it sees. Signal carries the encrypted candidate exchange between peers. The clients test possible paths with ICE. Advance again. Once a path works, WireGuard carries the session. If a direct path fails, the native NetBird relay forwards the encrypted packets. Management and Signal don’t carry that application traffic. You can use NetBird Cloud or run these services yourself.

~2 min. Management knows the public keys, addresses, and access policy. The private key stays on the client. The account gets an IPv4 range within 100.64.0.0/10, separate from the usual private LAN ranges. That isn’t a promise that it can never overlap another VPN. Management distributes the network map, policies, and DNS configuration. The client applies the access rules locally. Joining the account and being allowed to reach a service are separate decisions. Check the actual policy, including any default policy, before assuming the network is restricted.

How NetBird works

Discover an address, then test it

STUN reports what it sees. ICE checks which candidate pairs actually work.

NC State Linux Users’ Group · October 16, 2026
Speaker notes and sources

~2 min. STUN sees the source address and port after NAT has rewritten them. Those example ports are 33978 and 48654. They are candidates, not proof that the other peer can reach us there. The client also knows local interface addresses. Signal passes the candidate messages to the other peer, encrypted between the clients. The peers then test candidate pairs with ICE and nominate a working pair. The pair selection uses priorities and connectivity checks; it isn’t simply whichever packet answers first. Signal remains available for coordination when connections need to change, even though it doesn’t carry the WireGuard session.

UDP hole punching

Stable mappings help. Destination-dependent mappings or blocked UDP can defeat the direct path.

NC State Linux Users’ Group · October 16, 2026
Speaker notes and sources

~3 min. Here’s the hole punch. Both machines send outbound probes to the candidate address on the other side. The NATs create mappings, and their filtering rules decide whether the return packets can pass. An early probe can be dropped before the other side has sent anything. Probes repeat, so this doesn’t need perfect timing. Endpoint-independent mapping helps because the public endpoint stays usable across destinations. Endpoint-dependent mapping, often called symmetric NAT, can give you a different port when you talk to the peer than when you talked to STUN. Filtering matters too, so NAT type alone isn’t the whole story. If a working direct pair can’t be established, the relay gives us another path.

The relay carries encrypted packets

Two transports race

QUIC over UDP/443 and WebSocket over TCP/443. The first connection wins.

A separate fallback path

The native relay is separate from ICE. An ICE relay candidate means legacy TURN.

A relay can change latency and throughput. It cannot decrypt the WireGuard payload.

NC State Linux Users’ Group · October 16, 2026
Speaker notes and sources

~2 min. If the direct path is unavailable, both peers use a relay connection. WireGuard encryption stays between the endpoints. The relay forwards ciphertext. Current clients try QUIC and WebSocket in parallel and keep whichever connects first. WebSocket can win while UDP is working. Allowing TCP 443 helps, but a proxy or TLS inspection can still interfere. The native relay is a separate path from ICE. The relay candidate type in ICE is the legacy TURN path, not this native relay. In status output, a native relayed connection normally shows no selected ICE candidate pair. We’ll look for that in the demo.
