I wanted Seafile running in its own VM, with my files on Unraid and HTTPS handled by the Nginx Proxy Manager instance I already use. That sounds pretty simple, but there are a few pieces to connect: the storage mount, database, document editor, and notification service all need to agree on where things live.

In this guide, we'll build that setup with Seafile Community Edition 13, Fedora Server, and Docker Compose. We'll also include SeaDoc for editing documents in the browser and Seafile's notification server for real-time library updates. Everything will be available through one address, such as `https://seafile.example.com`.

I've also included an optional OnlyOffice setup for Word, Excel, and PowerPoint files, followed by the steps I used to bring an existing Nextcloud folder into a Seafile library. The migration runs inside the VM, so your computer doesn't have to relay several terabytes of files.

My deployment ran Seafile **13.0.25** and SeaDoc **2.0.9**. The examples follow the 13.x configuration and use its update tags. I've combined the services into one Compose file to make the walkthrough easier to follow. This is a customized version of the [official Seafile 13 Docker setup](https://manual.seafile.com/13.0/setup/setup_ce_by_docker/), with an existing reverse proxy and separate local and Unraid storage.

## What we're building

Nginx Proxy Manager, or NPM, stays on your existing server. It accepts the HTTPS connection and forwards requests to port **8080** on the Seafile VM. A small NGINX container inside that VM sends each request to the right service.

```text
Your browser or Seafile client
          |
          | HTTPS: seafile.example.com
          v
Existing Nginx Proxy Manager
          |
          | HTTP: 192.168.1.50:8080
          v
NGINX gateway in the Fedora VM
          |
          +-- Seafile: files, accounts, and web interface
          +-- SeaDoc: collaborative document editor
          +-- Notification server: real-time updates

VM local disk                     Unraid share, mounted in the VM
/srv/seafile                      /mnt/seafile
  Compose files                     Seafile files and configuration
  Live MariaDB database             SeaDoc persistent files
```

The base setup shown above has six containers: those three application services, MariaDB, Redis, and the NGINX gateway. Only the gateway publishes a port on the VM. The optional OnlyOffice section adds a seventh container, reached through `/office/` on the same domain.

## Before you start

This walkthrough assumes a **new, dedicated Fedora Server VM on Unraid**. It is a fresh installation guide, so don't paste these files over an existing Seafile deployment without reviewing its configuration first.

You'll need:

- An x86-64 Fedora Server VM. I used Fedora 44 and four virtual CPUs across two physical cores. The base setup worked with 4 GB of RAM; I increased it to **8 GB before adding OnlyOffice**.
- A local virtual disk with room for Fedora, container images, the database, and working files. I used a 64 GB disk. If you're adding OnlyOffice, allow at least **40 GB of free space** inside Fedora; an 80 GB or larger virtual disk gives a new combined installation more headroom.
- An Unraid user share named `seafile`, with enough space for your files.
- An existing NPM instance that can reach the VM over your network.
- A domain you control, with its Seafile hostname pointing to NPM.
- A Fedora account with `sudo` access and basic familiarity with SSH.

Seafile lists two CPU cores and 2 GB of memory for CE, with additional resources needed for extra services. See its [system requirements](https://manual.seafile.com/13.0/setup/system_requirements/) when sizing a larger installation.

Use these examples consistently as you go:

| Setting | Example | What to use |
| --- | --- | --- |
| VM address | `192.168.1.50` | Your Fedora VM's LAN address |
| Public hostname | `seafile.example.com` | Your actual Seafile domain |
| Administrator | `you@example.com` | Your email address |
| VM hostname | `fedora-seafile` | This can stay as shown |
| Unraid mount tag | `seafile` | Must match the VM share setting |

Reserve the VM's address in your router or DHCP server so NPM's forwarding target doesn't change after a reboot.

Unless a step specifically says **Unraid**, **NPM**, or **your computer**, run its commands in the **Fedora VM over SSH**. We'll use `nano` to edit files. In nano, save with **Ctrl+O**, press **Enter**, then exit with **Ctrl+X**.

## 1. Prepare the VM in Unraid

Shut down the VM before changing its hardware settings. In Unraid's VM editor, set the CPU mode to **Host Passthrough** and assign at least two CPU cores. My setup uses two cores and their matching threads, giving Fedora four virtual CPUs.

This fixed an issue I ran into during installation: the VM's generic QEMU CPU model hid instructions needed by a bundled Python dependency. The login page loaded, but an API request returned an error about `X86_V2`. Host Passthrough exposed the real CPU features. The physical CPU still needs to support the instructions the software requires.

Add the Unraid share with these settings:

| Unraid VM setting | Value |
| --- | --- |
| Unraid Share Mode | `9p Mode` |
| Unraid Share | `User:seafile` |
| Unraid Source Path | `/mnt/user/seafile/` |
| Unraid Mount Tag | `seafile` |

Start the VM and reconnect with SSH. Set its hostname:

```bash
sudo hostnamectl set-hostname fedora-seafile
```

The VM hostname is its Linux system name. Your public Seafile domain is a separate setting we'll configure later.

## 2. Understand `/srv` versus `/mnt`

Here's the storage split we're going to use:

| Path inside Fedora | Underlying storage | Purpose |
| --- | --- | --- |
| `/srv/seafile` | VM's local virtual disk | Compose project, environment file, and proxy configuration |
| `/srv/seafile/mysql` | VM's local virtual disk | Live MariaDB database |
| `/srv/seafile/onlyoffice` | VM's local virtual disk | Optional OnlyOffice configuration, fonts, logs, and working cache |
| `/srv/seafile/migration` | VM's local virtual disk | Temporary migration client configuration, index, and block cache |
| `/mnt/seafile/seafile-data` | Unraid share | Seafile's stored file blocks, application configuration, and logs |
| `/mnt/seafile/seadoc-data` | Unraid share | SeaDoc's persistent directory, including logs |
| `/mnt/archive-source` | Separate SMB mount from the NAS | Read-only source folder during the optional migration |

`/srv` is a conventional place for service-related data. `/mnt` is a conventional place to mount another filesystem. **The directory names don't move data onto a different disk.** Mounting the Unraid share at `/mnt/seafile` is what makes files written there land on Unraid.

I'm keeping MariaDB local because it does frequent small reads and writes and depends on reliable filesystem behavior. A local Linux filesystem is a more straightforward home for that workload than the VM's 9p share.

OnlyOffice's working files stay local for the same general reason. Once the editor saves a document back to Seafile, that document is stored on Unraid with the rest of the library. Its working cache can contain edits awaiting a save, so we'll also give it time to finish saving during shutdown.

Also, putting the Compose project in `/srv/seafile` doesn't relocate Docker itself. Docker's images, writable container layers, and runtime storage still use its local defaults, including `/var/lib/docker` and, depending on the installation, containerd's storage.

One other detail: Seafile manages files using its own storage format. You won't find a regular folder tree of your uploaded documents under `seafile-data`. Upload existing files through Seafile's web interface or client. Don't copy a collection of documents into that directory and expect them to appear in your libraries.

## 3. Mount the Unraid share inside Fedora

The 9p share is passed from Unraid to the VM through the virtual hardware. You don't enter an SMB server address or mount it using Unraid's IP. The name `seafile` below is the **mount tag** from the VM settings. Linux documents this transport in its [9p filesystem guide](https://docs.kernel.org/filesystems/9p.html).

Create the mount point and try the mount:

```bash
sudo mkdir -p /mnt/seafile
sudo mount -t 9p -o trans=virtio,version=9p2000.L,cache=none seafile /mnt/seafile
findmnt /mnt/seafile
```

You should see `/mnt/seafile` with filesystem type `9p` and source `seafile`. If that fails, stop here and check the Unraid mount tag before creating application folders.

Test that your normal Fedora user can write to the share:

```bash
touch /mnt/seafile/.write-test
rm /mnt/seafile/.write-test
```

If you get a permission error, check the Unraid share's ownership and permissions for the mapped VM user. Don't apply a recursive `chmod 777` to your NAS to work around it.

Make the mount persistent. Back up the existing file, then open it:

```bash
sudo cp -a /etc/fstab /etc/fstab.before-seafile
sudo nano /etc/fstab
```

Add this as **one new line**, keeping the existing entries:

```text
seafile /mnt/seafile 9p trans=virtio,version=9p2000.L,cache=none,rw,nofail,x-systemd.mount-timeout=30s 0 0
```

Check the file and reload systemd:

```bash
sudo findmnt --verify
sudo systemctl daemon-reload
sudo systemctl start mnt-seafile.mount
findmnt /mnt/seafile
```

`nofail` lets Fedora finish booting if the share is unavailable. Later, we'll tell Docker and Seafile to require the mount. That way, you can still reach the VM to fix storage without letting the application write into an empty local mount point.

## 4. Install Docker and create the folders

Install Docker Engine and its Compose plugin using the [official Fedora instructions](https://docs.docker.com/engine/install/fedora/):

```bash
sudo dnf install -y dnf-plugins-core nano curl openssl
sudo dnf config-manager addrepo --from-repofile https://download.docker.com/linux/fedora/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
```

Use `docker compose` with a space. We'll run it with `sudo`, so you don't need to change your user's Docker group membership for this guide. If Docker reports a package conflict on a VM you've used before, review the conflict guidance on that Fedora installation page.

Check your user's numeric IDs:

```bash
id -u
id -g
```

The following commands assume both are **1000**. If yours differ, substitute your IDs in the ownership commands. We want the **project directory** owned by `1000:1000`; each container can still manage the ownership it needs for its own data.

```bash
sudo install -d -o 1000 -g 1000 -m 0750 /srv/seafile
sudo install -d -m 0750 /srv/seafile/mysql
```

Confirm the share is mounted, then create its application directories:

```bash
mountpoint /mnt/seafile
```

Only continue when that reports that `/mnt/seafile` is a mount point:

```bash
sudo mkdir -p /mnt/seafile/seafile-data/seafile/logs
sudo mkdir -p /mnt/seafile/seadoc-data
cd /srv/seafile
```

Don't recursively change `/srv/seafile` to `1000:1000` after the database has started. MariaDB will set its data directory's ownership for the user inside its container. For the same reason, we aren't adding `user: "1000:1000"` to every service.

## 5. Create the environment file

The `.env` file holds the settings Compose will insert into the container configuration. We'll generate separate random passwords automatically, then edit the domain, IP, email, and time zone.

Run this whole block from `/srv/seafile`. It is for the **first setup only**, since running it again would overwrite your saved settings and passwords.

```bash
umask 077
cat > .env << EOF
COMPOSE_PROJECT_NAME=seafile

SEAFILE_BIND_IP=192.168.1.50
SEAFILE_SERVER_HOSTNAME=seafile.example.com
SEAFILE_SERVER_PROTOCOL=https
TIME_ZONE=America/Los_Angeles

SEAFILE_IMAGE=seafileltd/seafile-mc:13.0-latest
SEAFILE_DB_IMAGE=mariadb:10.11
SEAFILE_REDIS_IMAGE=redis:7.4-alpine
SEADOC_IMAGE=seafileltd/sdoc-server:2.0-latest
NOTIFICATION_SERVER_IMAGE=seafileltd/notification-server:13.0-latest
GATEWAY_IMAGE=nginx:stable-alpine

SEAFILE_VOLUME=/mnt/seafile/seafile-data
SEADOC_VOLUME=/mnt/seafile/seadoc-data
SEAFILE_MYSQL_VOLUME=/srv/seafile/mysql

JWT_PRIVATE_KEY=$(openssl rand -hex 32)
SEAFILE_MYSQL_DB_PASSWORD=$(openssl rand -hex 24)
INIT_SEAFILE_MYSQL_ROOT_PASSWORD=$(openssl rand -hex 24)
REDIS_PASSWORD=$(openssl rand -hex 24)
INIT_SEAFILE_ADMIN_EMAIL=you@example.com
INIT_SEAFILE_ADMIN_PASSWORD=$(openssl rand -hex 24)

ENABLE_SEADOC=true
ENABLE_NOTIFICATION_SERVER=true
EOF
nano .env
```

Replace `SEAFILE_BIND_IP`, `SEAFILE_SERVER_HOSTNAME`, and `INIT_SEAFILE_ADMIN_EMAIL` with your values. Set your time zone too. The hostname must contain just the domain, without `https://` or a trailing slash.

Copy `INIT_SEAFILE_ADMIN_PASSWORD` into your password manager before closing the file. Leave `SEAFILE_SERVER_PROTOCOL=https`: that's the address your browser will use, even though NPM connects to the VM over HTTP.

The `JWT_PRIVATE_KEY` is a shared secret used by Seafile and its add-ons to authenticate requests between them. Our Compose file passes the same value to all three services. You don't need to create a PEM file or generate separate keys for each container.

The `INIT_` administrator settings initialize a new installation. Editing them later doesn't reset an existing account's password. Keep `.env` private and out of Git repositories.

## 6. Add the Compose file

Create the file:

```bash
nano compose.yaml
```

Paste the complete configuration below. It is long because it includes all six services, health checks, and explicit storage mounts. You shouldn't need to edit it if you used the paths above and customized `.env`.

```yaml
services:
  db:
    image: ${SEAFILE_DB_IMAGE}
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${INIT_SEAFILE_MYSQL_ROOT_PASSWORD:?Set in .env}
      MYSQL_LOG_CONSOLE: "true"
      MARIADB_AUTO_UPGRADE: "1"
    volumes:
      - type: bind
        source: ${SEAFILE_MYSQL_VOLUME}
        target: /var/lib/mysql
        bind:
          create_host_path: false
    healthcheck:
      test: ["CMD", "/usr/local/bin/healthcheck.sh", "--connect", "--mariadbupgrade", "--innodb_initialized"]
      interval: 20s
      timeout: 5s
      retries: 10
      start_period: 30s
    logging:
      driver: local
      options:
        max-size: "10m"
        max-file: "3"

  redis:
    image: ${SEAFILE_REDIS_IMAGE}
    restart: unless-stopped
    environment:
      REDIS_PASSWORD: ${REDIS_PASSWORD:?Set in .env}
    command:
      - /bin/sh
      - -c
      - exec redis-server --requirepass "$$REDIS_PASSWORD" --save "" --appendonly no
    healthcheck:
      test: ["CMD-SHELL", "REDISCLI_AUTH=\"$$REDIS_PASSWORD\" redis-cli ping | grep -q PONG"]
      interval: 20s
      timeout: 5s
      retries: 5
    logging:
      driver: local
      options:
        max-size: "10m"
        max-file: "3"

  seafile:
    image: ${SEAFILE_IMAGE}
    restart: unless-stopped
    volumes:
      - type: bind
        source: ${SEAFILE_VOLUME}
        target: /shared
        bind:
          create_host_path: false
    environment:
      SEAFILE_MYSQL_DB_HOST: db
      SEAFILE_MYSQL_DB_PORT: "3306"
      SEAFILE_MYSQL_DB_USER: seafile
      SEAFILE_MYSQL_DB_PASSWORD: ${SEAFILE_MYSQL_DB_PASSWORD:?Set in .env}
      INIT_SEAFILE_MYSQL_ROOT_PASSWORD: ${INIT_SEAFILE_MYSQL_ROOT_PASSWORD:?Set in .env}
      SEAFILE_MYSQL_DB_CCNET_DB_NAME: ccnet_db
      SEAFILE_MYSQL_DB_SEAFILE_DB_NAME: seafile_db
      SEAFILE_MYSQL_DB_SEAHUB_DB_NAME: seahub_db
      INIT_SEAFILE_ADMIN_EMAIL: ${INIT_SEAFILE_ADMIN_EMAIL:?Set in .env}
      INIT_SEAFILE_ADMIN_PASSWORD: ${INIT_SEAFILE_ADMIN_PASSWORD:?Set in .env}
      SEAFILE_SERVER_HOSTNAME: ${SEAFILE_SERVER_HOSTNAME:?Set in .env}
      SEAFILE_SERVER_PROTOCOL: ${SEAFILE_SERVER_PROTOCOL}
      TIME_ZONE: ${TIME_ZONE}
      JWT_PRIVATE_KEY: ${JWT_PRIVATE_KEY:?Set in .env}
      NON_ROOT: "false"
      CACHE_PROVIDER: redis
      REDIS_HOST: redis
      REDIS_PORT: "6379"
      REDIS_PASSWORD: ${REDIS_PASSWORD:?Set in .env}
      ENABLE_SEADOC: ${ENABLE_SEADOC}
      SEADOC_SERVER_URL: ${SEAFILE_SERVER_PROTOCOL}://${SEAFILE_SERVER_HOSTNAME}/sdoc-server
      ENABLE_NOTIFICATION_SERVER: ${ENABLE_NOTIFICATION_SERVER}
      INNER_NOTIFICATION_SERVER_URL: http://notification-server:8083
      NOTIFICATION_SERVER_URL: ${SEAFILE_SERVER_PROTOCOL}://${SEAFILE_SERVER_HOSTNAME}/notification
      ENABLE_SEAFILE_AI: "false"
      ENABLE_FACE_RECOGNITION: "false"
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS -H \"Host: $$SEAFILE_SERVER_HOSTNAME\" http://localhost:80/api2/server-info/ > /dev/null"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 180s
    logging:
      driver: local
      options:
        max-size: "10m"
        max-file: "3"

  seadoc:
    image: ${SEADOC_IMAGE}
    restart: unless-stopped
    volumes:
      - type: bind
        source: ${SEADOC_VOLUME}
        target: /shared
        bind:
          create_host_path: false
    environment:
      DB_HOST: db
      DB_PORT: "3306"
      DB_USER: seafile
      DB_PASSWORD: ${SEAFILE_MYSQL_DB_PASSWORD:?Set in .env}
      DB_NAME: seahub_db
      TIME_ZONE: ${TIME_ZONE}
      JWT_PRIVATE_KEY: ${JWT_PRIVATE_KEY:?Set in .env}
      NON_ROOT: "false"
      SEAHUB_SERVICE_URL: http://seafile
    depends_on:
      db:
        condition: service_healthy
      seafile:
        condition: service_healthy
    logging:
      driver: local
      options:
        max-size: "10m"
        max-file: "3"

  notification-server:
    image: ${NOTIFICATION_SERVER_IMAGE}
    restart: unless-stopped
    volumes:
      - type: bind
        source: ${SEAFILE_VOLUME}/seafile/logs
        target: /shared/seafile/logs
        bind:
          create_host_path: false
    environment:
      SEAFILE_MYSQL_DB_HOST: db
      SEAFILE_MYSQL_DB_PORT: "3306"
      SEAFILE_MYSQL_DB_USER: seafile
      SEAFILE_MYSQL_DB_PASSWORD: ${SEAFILE_MYSQL_DB_PASSWORD:?Set in .env}
      SEAFILE_MYSQL_DB_CCNET_DB_NAME: ccnet_db
      SEAFILE_MYSQL_DB_SEAFILE_DB_NAME: seafile_db
      JWT_PRIVATE_KEY: ${JWT_PRIVATE_KEY:?Set in .env}
    depends_on:
      db:
        condition: service_healthy
      seafile:
        condition: service_healthy
    logging:
      driver: local
      options:
        max-size: "10m"
        max-file: "3"

  gateway:
    image: ${GATEWAY_IMAGE}
    restart: unless-stopped
    ports:
      - "${SEAFILE_BIND_IP:?Set in .env}:8080:80"
    volumes:
      - type: bind
        source: /srv/seafile/gateway.conf
        target: /etc/nginx/conf.d/default.conf
        read_only: true
        bind:
          create_host_path: false
    depends_on:
      seafile:
        condition: service_healthy
      seadoc:
        condition: service_started
      notification-server:
        condition: service_started
    healthcheck:
      test: ["CMD-SHELL", "wget -q -O /dev/null http://127.0.0.1/api2/server-info/"]
      interval: 30s
      timeout: 10s
      retries: 3
    logging:
      driver: local
      options:
        max-size: "10m"
        max-file: "3"
```

Compose creates a private network for this project automatically. On that network, the service name `db` resolves to MariaDB, `seafile` resolves to Seafile, and so on. These names aren't public DNS records you need to create.

The `source` of each bind mount is a path on Fedora. The `target` is where that directory appears inside the container. `create_host_path: false` makes a missing source directory an error instead of silently creating one. We'll add a separate mount check too, because an existing directory alone doesn't prove Unraid is mounted.

The logging settings cap Docker's own container logs. Application log files written into the shared data directories have their own rotation behavior and still need disk space.

## 7. Add the internal NGINX gateway

Create the gateway configuration:

```bash
nano gateway.conf
```

Paste this file exactly as shown. It uses the incoming domain automatically, so there is no example hostname to replace here.

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}

server {
    listen 80 default_server;
    server_name _;
    server_tokens off;

    client_max_body_size 0;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Proto https;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
    proxy_buffering off;
    proxy_request_buffering off;

    location /sdoc-server/ {
        proxy_pass http://seadoc:80/;
    }

    location /socket.io {
        proxy_pass http://seadoc:80;
    }

    location = /notification {
        proxy_pass http://notification-server:8083/;
    }

    location /notification/ {
        proxy_pass http://notification-server:8083/;
    }

    location / {
        proxy_pass http://seafile:80;
    }
}
```

The gateway keeps the NPM side pretty simple: one domain and one forwarding port. Seafile gets the normal application requests, while the other locations handle SeaDoc and notifications.

Keep the trailing slashes as shown. For example, `/notification/ping` needs to arrive at the notification container as `/ping`. The WebSocket headers allow the persistent connections used by the add-ons. This follows the routing described in Seafile's [external reverse proxy guide](https://manual.seafile.com/13.0/setup/use_other_reverse_proxy/) and [NGINX's WebSocket documentation](https://nginx.org/en/docs/http/websocket.html).

We explicitly forward `X-Forwarded-Proto https` because NPM handles the encrypted browser connection. Port 8080 is an HTTP backend for your trusted network; don't forward it directly from your internet router.

Check the Compose configuration without printing its resolved passwords:

```bash
chmod 600 .env
chmod 640 compose.yaml gateway.conf
sudo docker compose config --quiet
sudo docker compose pull
```

No output from `config --quiet` means validation passed. Image downloads can take a few minutes.

## 8. Make startup wait for Unraid

This step matters. If Docker starts before the share mounts, container restart policies can bring the application back before your storage is ready.

Since this is a **dedicated Seafile VM**, we'll make the Docker daemon itself depend on the share. This affects every Docker container on the VM. On a shared Docker host, you'd need a startup arrangement that accounts for its other applications too.

Create a Docker service override:

```bash
sudo mkdir -p /etc/systemd/system/docker.service.d
sudo nano /etc/systemd/system/docker.service.d/seafile-storage.conf
```

```ini
[Unit]
RequiresMountsFor=/mnt/seafile
BindsTo=mnt-seafile.mount
After=mnt-seafile.mount
```

Now create a systemd service for the Compose project:

```bash
sudo nano /etc/systemd/system/seafile.service
```

```ini
[Unit]
Description=Seafile Docker Compose stack
Requires=docker.service
Wants=network-online.target
After=docker.service network-online.target mnt-seafile.mount
RequiresMountsFor=/mnt/seafile /srv/seafile
BindsTo=mnt-seafile.mount
PartOf=docker.service

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/srv/seafile
ExecStartPre=/usr/bin/mountpoint -q /mnt/seafile
ExecStart=/usr/bin/docker compose up -d --wait --wait-timeout 360
ExecStop=/usr/bin/docker compose down --timeout 60
TimeoutStartSec=600
TimeoutStopSec=180

[Install]
WantedBy=multi-user.target
```

This tells systemd where the project lives, checks the mount, and starts the containers. The mount dependency controls ordering, while `BindsTo` stops the dependent service if systemd sees the mount go away.

Start everything:

```bash
sudo systemctl daemon-reload
sudo systemctl restart docker
sudo systemctl enable --now seafile.service
sudo docker compose ps
```

The first start creates the databases, initial administrator, and application configuration. Give it a few minutes. The database, Redis, Seafile, and gateway should become healthy; SeaDoc and the notification server should be running. We'll check the add-ons through HTTPS shortly.

If startup fails, read the logs before changing anything:

```bash
sudo journalctl -u seafile.service -n 80 --no-pager
sudo docker compose logs --tail=100 db seafile
```

For a slow first initialization, inspect the logs and retry with `sudo systemctl restart seafile.service` once you've resolved the issue. You don't need to delete the database and start over.

## 9. Point Nginx Proxy Manager at the VM

In your **existing NPM interface**, create a Proxy Host with these settings:

| NPM field | Value |
| --- | --- |
| Domain Names | Your domain, such as `seafile.example.com` |
| Scheme | `http` |
| Forward Hostname / IP | Your Fedora VM, such as `192.168.1.50` |
| Forward Port | `8080` |
| Websockets Support | Enabled |
| Cache Assets | Disabled |

In the **SSL** tab, select or request a valid certificate for the domain and enable **Force SSL**. Your DNS and certificate-validation method need to work with your existing NPM setup.

In the **Advanced** tab, add:

```nginx
client_max_body_size 0;
proxy_request_buffering off;
proxy_buffering off;
proxy_read_timeout 3600s;
proxy_send_timeout 3600s;
```

These settings remove NGINX's request-body size cap and give transfers longer timeouts. Other services in front of NPM, such as a CDN, may still impose their own limits.

You don't need extra NPM Custom Locations with this configuration. The gateway in the VM already handles `/sdoc-server/`, `/socket.io`, and `/notification`.

Save the proxy host and open your HTTPS domain. Log in with the email and generated administrator password from `.env`.

## 10. Upload files and try document editing

Before adding your real files, make a temporary library and upload a small document or image. Download it again and check the contents. Then try a larger file representative of what you normally store.

### SeaDoc: documents in the browser

In a library, use the **New** menu to create a SeaDoc document. Enter a few lines, wait for saving to finish, close it, then reopen it. Your text should still be there. If you plan to collaborate, share a test document with a second account and try editing from two browser sessions.

SeaDoc edits Seafile's `.sdoc` documents. Its persistent directory includes logs, while document contents live in Seafile and its operation log uses the existing `seahub_db` database. It doesn't need a separate `sdoc_db` for this version. The [Seafile 13 SeaDoc instructions](https://manual.seafile.com/13.0/extension/setup_seadoc/) explain that integration.

This is useful for notes and shared documentation. Opening an uploaded Word document is a separate feature: SeaDoc doesn't provide the browser viewer for `.docx` files. With just the base setup, you can store, sync, and download those files, but Seafile may display **"Online view is not applicable to this file format"** when you try to preview one.

#### Optional: OnlyOffice or Collabora for Office files

Seafile supports two additional office suites for viewing and editing documents in the browser:

- **[OnlyOffice Docs](https://manual.seafile.com/13.0/extension/only_office/)** provides editors for Word, Excel, and PowerPoint formats, including `.docx`, `.xlsx`, and `.pptx`. The component you want for this integration is **Document Server**.
- **[Collabora Online](https://manual.seafile.com/13.0/extension/collabora_online/)** is a LibreOffice-based alternative that supports Microsoft Office and OpenDocument formats. Its free [CODE edition](https://www.collaboraonline.com/code/) is intended for development, home use, and small teams; the supported production edition is a separate offering.

Either can work alongside SeaDoc. Both require an additional office service, a connection to Seafile, and reverse proxy configuration. Enabling SeaDoc alone doesn't enable either integration.

I chose OnlyOffice for this deployment and tested opening, editing, saving, and reopening a DOCX file. The steps below add it to the existing Compose project. Collabora remains an alternative if you prefer its editors; follow its linked integration guide instead of installing both for the same file types.

#### Route `/office/` through the existing gateway

Open `/srv/seafile/gateway.conf`. Add these locations **inside the existing `server` block**, above `location /`:

```nginx
    location = /office {
        return 301 /office/;
    }

    location /office/ {
        resolver 127.0.0.11 valid=30s ipv6=off;
        set $office_backend http://onlyoffice:80;
        rewrite ^/office/(.*)$ /$1 break;
        proxy_pass $office_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Host $host/office;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
    }
```

The browser requests `/office/...`, while the gateway removes that prefix before forwarding to Document Server. The forwarded host includes `/office` so the editor generates the right public URLs, following [OnlyOffice's virtual-path proxy example](https://github.com/ONLYOFFICE/document-server-proxy/blob/master/nginx/proxy-to-virtual-path.conf). Docker's DNS resolver lets NGINX resolve the optional service when a request arrives.

Keep this path as **`/office/`**. Seafile uses `/onlyoffice/` for its own integration endpoints, so routing that whole prefix to Document Server would break callbacks. Your NPM proxy host still forwards to the same VM address and port **8080**, with WebSockets enabled; no additional domain or Custom Location is needed.

```bash

sudo docker compose pull onlyoffice
sudo docker compose up -d --wait --wait-timeout 360 onlyoffice
sudo docker compose exec -T gateway nginx -t
sudo docker compose exec -T gateway nginx -s reload
```

Once startup and the NGINX configuration check succeed, connect the editor to Seafile below. If either command fails, check `sudo docker compose logs --tail=100 onlyoffice gateway`.

## 12. Optional: move a Nextcloud folder into a Seafile library

For my migration, the files were already available through an SMB network share. I wanted the contents of `ncdata/__groupfolders/1/files` to become the contents of a new **Archive** library in Seafile, keeping the folder structure underneath it.

We'll mount that exact folder read-only in the Seafile VM and use Seafile's Linux command-line client to upload it. This is a **file migration**: it doesn't bring over Nextcloud accounts, shares, permissions, comments, or version history. The source must expose normal, readable files. If Nextcloud encryption or another storage backend hides the originals, export readable files through Nextcloud first.

### How the files travel

```text
NAS SMB share, read-only
  //192.168.1.10/ncdata/__groupfolders/1/files
              |
              | LAN read
              v
Seafile client running in the Fedora VM
  /mnt/archive-source
              |
              | Upload to https://seafile.example.com
              v
Existing NPM -> VM gateway -> Seafile's Archive library
                                      |
                                      v
                          Unraid /mnt/seafile storage
```

Your laptop or desktop only controls the job over SSH. The files travel between the NAS, VM, and reverse proxy. With the Seafile hostname resolving to NPM's LAN address, that traffic stays on the LAN. If you use a CDN or other external proxy, check the VM's DNS and routing before starting a multi-terabyte transfer.

Seafile writes its own blocks on the destination share. This requires space for the new library while the original files still exist, even when both shares live on the same NAS. It also means the NAS handles both source reads and destination writes. Don't copy the source directly into Seafile's internal `seafile-data` directory.

### Prepare an empty destination and a stable source

In Seafile's web interface, create an **empty, unencrypted library named Archive**. Leave it unused by other people and clients until the migration is finished and disconnected. This procedure uses a synchronization client, so changes made on either side can affect what it tries to synchronize.

Stop editing the Nextcloud source during the copy, or use a read-only snapshot of the source where your storage supports one. Our read-only SMB mount protects against writes from this VM; it doesn't prevent Nextcloud or another NAS client from changing the original files.

In the examples below, replace `192.168.1.10`, the share/subfolder path, and `nasuser` with your values. Run everything in the **Seafile VM**.

```bash
sudo dnf install -y cifs-utils python3 python3-requests
sudo install -d -m 0750 /mnt/archive-source
sudo mount -t cifs //192.168.1.10/ncdata/__groupfolders/1/files \
  /mnt/archive-source \
  -o ro,username=nasuser,vers=3.1.1,uid=1000,gid=1000,nosuid,nodev,noexec,cache=strict
```

Enter the **SMB account's password** at the prompt. It stays out of the command and shell history. The path includes the folder inside the share, so `files` itself won't become an extra folder inside Archive.

Check the mount and its contents before proceeding:

```bash
findmnt -T /mnt/archive-source -o TARGET,SOURCE,FSTYPE,OPTIONS
sudo ls -la /mnt/archive-source
```

Expect the target `/mnt/archive-source`, filesystem `cifs`, and the `ro` option. The listing must show the folders you want inside Archive. I caught a mount that exposed the top of `ncdata` instead of the intended subfolder during setup; checking here prevented uploading the wrong tree.

### Record the source size and file list

Create a private working directory on the VM's local disk. Substitute your user IDs if they differ from `1000:1000`:

```bash
sudo install -d -o 1000 -g 1000 -m 0700 /srv/seafile/migration
mkdir -p /srv/seafile/migration/tools /srv/seafile/migration/client
```

This inventory records relative paths, sizes, and modification times without reading every file's contents. Run the whole block:

```bash
sudo python3 - << 'PY'
from json import dumps
from os import umask, walk
from pathlib import Path

umask(0o077)
source = Path('/mnt/archive-source')
if not source.is_mount():
    raise SystemExit('Source is not mounted; stop and fix the mount.')
work = Path('/srv/seafile/migration')
totals = {'files': 0, 'directories': 0, 'bytes': 0}

def stop_on_error(error):
    raise error

with (work / 'source-manifest.jsonl').open('w') as manifest:
    for parent, directories, files in walk(source, onerror=stop_on_error):
        for name in directories + files:
            path = Path(parent) / name
            if path.is_symlink():
                raise SystemExit(f'Review symbolic link before migration: {path}')
            info = path.stat()
            kind = 'dir' if path.is_dir() else 'file'
            if kind == 'file' and not path.is_file():
                raise SystemExit(f'Review non-regular file: {path}')
            row = {'path': str(path.relative_to(source)), 'type': kind,
                   'size': info.st_size if kind == 'file' else 0,
                   'mtime_ns': info.st_mtime_ns}
            manifest.write(dumps(row) + '\n')
            totals['directories' if kind == 'dir' else 'files'] += 1
            if kind == 'file':
                totals['bytes'] += info.st_size
(work / 'source-inventory.json').write_text(dumps(totals, indent=2) + '\n')
print(dumps(totals, indent=2))
PY
```

Don't start the transfer if this reports an unreadable folder or another error. Keep both inventory files for comparison after the copy. My source turned out to contain **10,675 files totaling 4.58 TB**, which was larger than my initial estimate.

### Install the native Seafile client

I used the official x86-64 CLI AppImage, version **9.0.21**, with Seafile Server 13.0.25. Client and server version numbers don't need to match. The [Seafile download page](https://www.seafile.com/en/download/) links the CLI package.

```bash
cd /srv/seafile/migration/tools
curl -fL --retry 3 \
  -o Seafile-cli-x86_64-9.0.21.AppImage \
  https://sos-ch-dk-2.exo.io/seafile-downloads/Seafile-cli-x86_64-9.0.21.AppImage
chmod 755 Seafile-cli-x86_64-9.0.21.AppImage
./Seafile-cli-x86_64-9.0.21.AppImage --appimage-extract
sudo mv squashfs-root /opt/seafile-cli-9.0.21
sudo chown -R root:root /opt/seafile-cli-9.0.21
sudo restorecon -RF /opt/seafile-cli-9.0.21
```

Extracting the AppImage lets systemd run the client without a FUSE mount. Putting the executable under `/opt` and restoring its normal Fedora labels also avoids the SELinux execution denial I encountered when running it as a service from `/srv`. These installation commands are for the first run; don't move another extraction over an existing installation.

Create a small shortcut so you don't need to repeat the client paths in every command:

```bash
sudo nano /usr/local/bin/seafile-migrate
```

```bash
#!/usr/bin/env bash
export APPDIR=/opt/seafile-cli-9.0.21
exec "$APPDIR/AppRun" "$@" -c /srv/seafile/migration/client-config
```

Install its permissions and initialize the isolated client:

```bash
sudo chmod 755 /usr/local/bin/seafile-migrate
sudo restorecon /usr/local/bin/seafile-migrate
sudo seafile-migrate init -d /srv/seafile/migration/client
```

Let `init` create `client-config`; don't create that directory beforehand. The client keeps its index and temporary blocks under `/srv/seafile/migration`, while its working folder will be the already-mounted SMB source. It doesn't need a complete second staging copy on the VM, but the cache still needs free space.

### Run the client in the background with systemd

Create the service:

```bash
sudo nano /etc/systemd/system/seafile-archive-client.service
```

```ini
[Unit]
Description=Seafile client for Archive migration
After=network-online.target seafile.service mnt-archive\x2dsource.mount
Wants=network-online.target
RequiresMountsFor=/mnt/archive-source /mnt/seafile
BindsTo=mnt-archive\x2dsource.mount

[Service]
Type=simple
Environment=SEAFILE_SSL_CA_PATH=/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
Environment=APPDIR=/opt/seafile-cli-9.0.21
Environment=LD_LIBRARY_PATH=/opt/seafile-cli-9.0.21/usr/lib
ExecStartPre=/usr/bin/mountpoint -q /mnt/archive-source
ExecStart=/opt/seafile-cli-9.0.21/usr/bin/seaf-daemon -c /srv/seafile/migration/client-config -d /srv/seafile/migration/client/seafile-data -w /srv/seafile/migration/client/seafile
Restart=on-failure
RestartSec=15s
TimeoutStopSec=90
UMask=0077
Nice=5
```

Keep the literal `\x2d` in that mount-unit name. It's how systemd escapes the hyphen in `archive-source`. The mount dependency stops the client if systemd sees that source mount disappear.

The certificate-bundle path is for this Fedora installation. Check it exists, then start the service:

```bash
test -r /etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
sudo systemctl daemon-reload
sudo systemctl start seafile-archive-client.service
sudo systemctl status seafile-archive-client.service --no-pager
sudo seafile-migrate config -k delete_confirm_threshold -v 1
```

If the `test` command fails, find your distribution's trusted CA bundle before continuing. Seafile documents `SEAFILE_SSL_CA_PATH` in its [Linux client installation notes](https://help.seafile.com/syncing_client/install_linux_client/). This fixed a certificate-path issue on my VM while keeping HTTPS verification enabled.

The low deletion threshold adds a pause for deletion confirmation; it doesn't turn synchronization into a dedicated upload-only mode. The empty destination, stable source, read-only mount, and final disconnect are still part of the procedure. Use this systemd service to manage the daemon, rather than also running `seaf-cli start`.

### Connect the source to Archive

List your remote libraries using your Seafile domain and account email:

```bash
sudo seafile-migrate list-remote \
  -s https://seafile.example.com -u you@example.com
```

Enter your **Seafile account password** at the prompt. Find Archive and copy its library ID. Confirm you're selecting the empty library you just created, then replace `YOUR_ARCHIVE_LIBRARY_ID` below:

```bash
sudo seafile-migrate sync \
  -l YOUR_ARCHIVE_LIBRARY_ID \
  -s https://seafile.example.com \
  -u you@example.com \
  -d /mnt/archive-source
```

The [native client's `sync` command](https://help.seafile.com/syncing_client/linux-cli/) connects an existing folder to a library. The initial message can say it's starting a download while it gets the remote library information. With our empty destination, the existing source files are then indexed and uploaded.

Once the job is running under systemd, you can disconnect SSH or turn off your computer. Leave the VM, NAS, and NPM running. This one-time source mount isn't saved in `/etc/fstab`, and the client service isn't enabled at boot: after a VM reboot, repeat the SMB mount, check its contents, and start the same service. Keep the client configuration so it can resume; don't initialize it again.

### Monitor progress and estimate the remaining time

Check the client from any later SSH session:

```bash
sudo seafile-migrate status
sudo tail -n 30 /srv/seafile/migration/client-config/logs/seafile.log
df -h / /mnt/seafile
sudo du -sh /srv/seafile/migration/client
```

For a live view, run `sudo watch -n 10 seafile-migrate status`. Press **Ctrl+C** to close the view; the transfer keeps running.

`committing` means the client is indexing files. `uploading` means a batch is being sent. **The displayed percentage is for the current batch, not the whole library**, so reaching 100% and starting another batch is normal. Upload speed can drop to zero while the next batch is prepared.

Check Archive's growing size in Seafile's library information alongside the source inventory. For an overall estimate, record the destination's saved size twice, several minutes apart. Divide the increase in saved bytes by the elapsed seconds, then use that average:

```text
Remaining seconds = (source bytes - destination saved bytes) / average bytes per second
Remaining hours   = remaining seconds / 3600
```

For example, 4.58 TB takes about **28 hours at a sustained 43 MiB/s overall**. At 70 MiB/s overall, it's about **17 hours**. These are transfer estimates before final verification. Small-file indexing, large files, source and destination disk activity, and pauses change the result. A brief 80 MiB/s upload burst doesn't mean the entire job will average that speed.

Watch local free space as well as NAS capacity. To pause the transfer if space gets low or you need maintenance:

```bash
sudo systemctl stop seafile-archive-client.service
```

Start the same service to resume after resolving the issue and confirming both mounts. Don't delete its cache or configuration to pause it.

### Verify the copy, then disconnect the source

Wait for the client to report **`synchronized`**, with no active errors, and check that Archive's file count and logical size agree with your source inventory. Compare nested folders, including empty ones, and check file modification times. File count alone isn't enough: a failed large file matters more than thousands of completed small ones.

Download a selection of files from Archive, including documents, images, and larger files from different folders. Open them, and compare checksums against the originals where practical. For a downloaded test file placed outside the source folder, use:

```bash
sha256sum /path/to/downloaded-test-file
sudo sha256sum /mnt/archive-source/path/to/original-file
```

The two hashes should match. Sampling gives useful confidence, but only reading and comparing every file provides a complete byte-for-byte check. Keep the original Nextcloud files until you're satisfied with verification and have a separate backup of the new Seafile installation.

Once verification is satisfactory, **disconnect synchronization while the source is still mounted**, then stop the client and unmount it:

```bash
sudo seafile-migrate desync -d /mnt/archive-source
sudo seafile-migrate list
```

Confirm Archive is no longer in the client's local library list before continuing:

```bash
sudo systemctl stop seafile-archive-client.service
sudo umount /mnt/archive-source
```

`desync` leaves the files in Seafile and on the NAS; it removes the synchronization relationship. Archive is now ready for normal use. This migration doesn't delete anything from Nextcloud.

Before updating, read the release notes and make a backup using your chosen backup setup. Once it completes, pull the images and recreate the stack:

```bash
cd /srv/seafile
sudo docker compose pull
sudo systemctl restart seafile.service
sudo docker compose ps
```

The `13.0-latest` tag follows Seafile's 13.0 series; it doesn't move you to the next major version. SeaDoc and the supporting containers have their own tags. OnlyOffice is pinned to the tested `9.4.0.1` tag here, so review its release notes and edit that tag deliberately when updating. For a major Seafile upgrade, follow the version-specific instructions in the manual and review the Compose changes too. Don't assume replacing every image tag is the entire upgrade process.

Keep an eye on both disks:

```bash
df -h / /mnt/seafile
sudo docker system df
```

File uploads go to Unraid, but the local database and container images still consume space inside the VM.

## A few problems worth checking first

| Symptom | First thing to check |
| --- | --- |
| `mount` can't find the 9p share | The Unraid VM mount tag must be `seafile`, and the share must be attached to this VM. |
| Docker won't start after a reboot | Run `findmnt /mnt/seafile` and `journalctl -u mnt-seafile.mount`. The storage dependency may be doing its job. |
| NPM shows a 502 error | Confirm the VM's reserved IP, port 8080, and `docker compose ps`. NPM needs a network route to that address. |
| Login page loads but requests return 500 | Read Seafile's logs. If they mention missing `X86_V2` CPU support, check the VM CPU mode. |
| SeaDoc opens but won't connect or save | Check `/sdoc-server/`, WebSocket support, the shared JWT, and the `seadoc` logs. |
| DOCX says online view isn't applicable | SeaDoc edits `.sdoc` files. Complete the optional OnlyOffice integration for Office previews. |
| OnlyOffice reports an invalid security token | The OnlyOffice JWT in `.env` and `seahub_settings.py` must match; restart the affected services after correcting it. |
| OnlyOffice opens but can't download or save | Check its access to the public Seafile hostname, certificate validation, private-IP setting, and `/office/` routing. |
| OnlyOffice stays unhealthy | Check its logs, VM resources, and that `local-production-linux.json` is readable at mode `644`. |
| Notification ping works but live updates don't | Check the `/notification` WebSocket connection for status 101. |
| Large uploads fail with 413 or time out | Check the body-size and timeout settings in both NPM and the gateway, plus any upstream proxy limits. |
| A bind mount reports permission denied | Check the specific directory's ownership and any SELinux denials before changing permissions. |
| Migration reports a TLS error | Check `SEAFILE_SSL_CA_PATH` and the certificate chain; don't disable verification. |
| Migration percentage repeatedly resets | It's a batch percentage. Check the growing destination library size for overall progress. |
| Migration service fails with `203/EXEC` | Check the `/opt/seafile-cli-9.0.21` path, executable permissions, and Fedora SELinux labels. |

My Fedora deployment kept SELinux enforcing. Don't disable it as a general installation step, and don't add `:Z` relabeling to the 9p mounts without understanding whether that filesystem supports the labels your Docker configuration needs.

### If an editor or live updates won't connect

These endpoint checks can help narrow down a proxy problem. Run them from your computer or the VM, replacing the example domain:

```bash
curl -fsS https://seafile.example.com/api2/ping/
curl -fsS https://seafile.example.com/sdoc-server/
curl -fsS https://seafile.example.com/notification/ping
```

Expect `pong`, a SeaDoc welcome response, and a response containing `"ret":"pong"`, respectively. If HTTPS validation fails, fix the certificate or hostname instead of adding `-k`.

If you installed OnlyOffice, check its route too:

```bash
curl -fsS https://seafile.example.com/office/healthcheck
curl -fsS -o /dev/null https://seafile.example.com/office/web-apps/apps/api/documents/api.js
```

The health check should return `true`; the second command should finish without an error. If either fails, check `sudo docker compose logs --tail=100 onlyoffice gateway` from `/srv/seafile`.

If the pings work but SeaDoc or live updates still won't connect, open your browser's developer tools, select **Network**, filter for **WS**, and reload the affected page. Look for `/notification` and, while editing a SeaDoc document, `/socket.io`. A successful WebSocket upgrade has status **101**.

## Where the advanced add-ons fit

The manual separates **Advanced topics** from **Extensions**. For this setup, the advanced pieces are using an existing reverse proxy and controlling startup around mounted storage. SeaDoc and the notification server are part of our base installation; the optional OnlyOffice section adds Office document editing through the same gateway.

If you're comparing this guide with the upstream files, the official deployment separates services into `seafile-server.yml`, `seadoc.yml`, and `notification-server.yml`, selected through `COMPOSE_FILE`. Its usual proxy configuration includes Caddy. Our single `compose.yaml` contains those application services and the NGINX gateway, with NPM handling the public certificate.

The [Extensions section](https://manual.seafile.com/13.0/extension/setup_seadoc/) also links to Collabora, WebDAV, and other integrations. Check their version and edition requirements if you add them. Our network-share migration uses the native Seafile client, so it doesn't need WebDAV or a direct import into the server's internal storage.

At this point, you can create your real libraries and connect a Seafile client using your HTTPS address. Start with a small library, confirm it syncs as expected, and then bring over the rest of your files.
