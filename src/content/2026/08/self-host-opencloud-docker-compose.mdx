I'm going to be upfront with you right at the top here. I'm a Nextcloud guy. I've run it for years, I like it, and it does a genuinely absurd amount of stuff for something you can install on a mini PC sitting in your closet. But I'm always willing to test out the competition, and OpenCloud has been sitting on my list for a while now.

So let's actually set it up properly. Real domain, real Let's Encrypt certificates, local storage on a path you control. Then I'll tell you what I honestly think of it compared to what I'm already running.

## Where OpenCloud Actually Comes From

Both Nextcloud and OpenCloud descend from ownCloud, but they came off completely different branches, and that matters more than you'd think.

Nextcloud is Frank Karlitschek's 2016 PHP fork of ownCloud Server. He founded ownCloud, left, forked it, and that fork grew into the full collaboration suite we all know today. It's AGPLv3.

OpenCloud comes from a totally different lineage. It's the continuation of ownCloud Infinite Scale, the Go rewrite that ownCloud started as a clean-slate replacement for the old PHP server. When Kiteworks acquired ownCloud in late 2023, the core oCIS engineering team left, and in January 2025 they relaunched the project as OpenCloud under the Heinlein Group in Berlin. The server is Apache 2.0, the clients are GPL, and there's no CLA, which is a detail I do appreciate if you've ever watched what happens to a project when one company owns all the copyright.

So these aren't two forks of the same codebase. One is a decade of PHP evolution, the other is a ground-up Go rewrite that just happens to share ancestry.

## Architecture Is the Real Difference

Nextcloud is a PHP monolith. It needs MariaDB or Postgres, it wants Redis for file locking and caching, it needs a cron worker, and at some point you will be tuning PHP memory limits and opcache. That's just the deal, and if you run it, you've made peace with it.

OpenCloud is Go microservices, and here's the part that actually made me pay attention: it stores metadata on the filesystem right next to the file data. There's no database instance to maintain. No schema migrations on upgrade. No coordinating a database dump with a filesystem snapshot and hoping the two line up.

For a homelab, that's a genuine operational simplification and I don't say that lightly. A ZFS snapshot of the data directory is your backup. That's it, that's the whole strategy. If you've ever restored a Nextcloud instance and found out your SQL dump was taken twenty minutes after your file snapshot, you know exactly why that's appealing.

The tradeoff is resource use and scope. OpenCloud runs comfortably on low-power hardware, where Nextcloud with a handful of apps enabled often wants 1 to 2 GB of RAM before it feels responsive.

## Scope Is the Other Real Difference

Nextcloud is a workspace. Talk, Calendar, Contacts, Mail, Deck, Flow, Assistant, plus a big third-party app store. OpenCloud is files, spaces, sharing, and search, with Collabora bolted on for document editing.

It does ship a Radicale integration for CalDAV and CardDAV, so you can get personal calendars and contacts out of it, and I'll show you how to turn that on later. But that's a personal calendar, not group calendaring with free/busy and room booking. If you need team workflows beyond files, Nextcloud is still the answer and it's not close.

## Maturity

Also not close, and I want to be fair here. Nextcloud has roughly 36,000 GitHub stars against OpenCloud's 5,700, and a decade of development versus about two years.

That gap shows up in the places you'd expect. Desktop and mobile client polish, documentation depth, third-party integrations, and the sheer volume of forum posts available when something breaks at 11pm and you need someone else to have hit it first.

OpenCloud is at 7.5.0 as of late August 2026 and they are shipping fast, which is fun to watch. But things like on-demand sync are still roadmap items, not features.

## How I'd Pick Between Them

Want a Google Drive replacement and nothing more, on modest hardware, with backups you can actually reason about? OpenCloud. Genuinely.

Want to replace Drive plus Calendar plus Contacts plus Meet, and you're fine paying for that in RAM and maintenance? Nextcloud.

And if you already run Nextcloud and it's working for you, there's no migration path worth the pain right now. The two share no storage format at all. This is a "spin it up alongside and poke at it" situation, not a "rip and replace on a Sunday afternoon" situation.

With all that, let's dive into the actual setup.

## What We're Building

Here's the target:

- OpenCloud on your own public domain, something like `cloud.yourdomain.com`
- Real Let's Encrypt certificates, issued and renewed automatically by Traefik
- Local filesystem storage on a host path you control, so backups are just a directory
- No S3, no MinIO, no external database

That last point tripped me up at first, so let me clarify it. The compose repo has a `storage/` folder, and people see that and assume they have to pick something. You don't. That folder contains exactly one file, `decomposeds3.yml`, and all it does is switch OpenCloud over to S3-backed storage. Leave it out and you get the default `decomposed` driver writing straight to local disk.

Local storage isn't a thing you turn on. It's what you get by not doing anything.

## What You Need

- A server with a public IP, ports 80 and 443 open and not already in use
- Docker and Docker Compose v2
- A domain you control, with access to its DNS
- Basic Docker comfort. You don't need to be an expert, but you should know what a compose file is

For this I'm on a small Debian VM, but any Linux box works. Proxmox VM, bare metal mini PC, a cheap VPS, whatever you've got sitting around.

Do note that Compose v2 is not optional here. Some distro repos, Debian 12 "Bookworm" included, still ship the old Python `docker-compose` v1, and running this repo against v1 gives you a broken deployment with genuinely confusing errors. Install from the official Docker repos:

```bash
curl -fsSL https://get.docker.com | sh
```

Then verify what you actually got:

```bash
docker compose version
```

You want `Docker Compose version v2.x.x`. If that says command not found but `docker-compose` works, you're on v1 and you need to sort that out before going any further.

## Point Your DNS at the Server

Before anything else, go ahead and create an A record:

```text
cloud.yourdomain.com.    A    203.0.113.10
```

Swap in your actual server IP. On IPv6, add an AAAA record too. Give it a minute and confirm:

```bash
dig +short cloud.yourdomain.com
```

Do this part first. Let's Encrypt uses the HTTP-01 challenge here, which means it hits `http://cloud.yourdomain.com/.well-known/acme-challenge/` and expects Traefik to answer. If DNS isn't live and those ports aren't reachable from the outside internet, cert issuance fails and you'll spend twenty minutes reading Traefik logs wondering what you broke. Ask me how I know.

## Clone the Repo

```bash
git clone https://github.com/opencloud-eu/opencloud-compose.git
cd opencloud-compose
```

Take a second and look around in there, because this repo is modular in a way I really like. `docker-compose.yml` is the core OpenCloud service, and everything else is an optional layer you stack on top using the `COMPOSE_FILE` variable.

- `traefik/` is the built-in reverse proxy, which is what we want
- `external-proxy/` is for when you already run nginx or Caddy
- `weboffice/` is Collabora or Euro Office
- `search/` is Apache Tika for full text search
- `idm/` is Keycloak and LDAP for real identity management
- `radicale/` is calendars and contacts
- `antivirus/` is ClamAV
- `storage/` is the S3 option we're deliberately skipping

You mix and match by listing files in `COMPOSE_FILE`, and later files override earlier ones. Pretty clean design, and it makes the whole thing easy to reproduce later.

## Create Your Local Storage Directories

This is the local storage part, and it's about as complicated as it sounds, which is to say not very:

```bash
sudo mkdir -p /srv/opencloud/{config,data}
sudo chown -R 1000:1000 /srv/opencloud
```

That `chown` is not optional and it's the single most common thing people trip over. The OpenCloud container runs as UID and GID 1000. If those directories are owned by root, the container starts, fails to write anything, and restart-loops forever while you stare at the logs trying to figure out what's wrong.

Two directories, two jobs:

- `config` is where `opencloud init` writes the generated config file with all your service secrets. It's small, but it is absolutely critical. Lose it and your instance is toast.
- `data` is where every file, all the metadata, and every space lives. This is the one that grows.

If you're on ZFS or Btrfs, this is your moment. Put `/srv/opencloud` on its own dataset:

```bash
sudo zfs create -o mountpoint=/srv/opencloud tank/opencloud
```

Then your entire backup strategy becomes `zfs snapshot tank/opencloud@daily` and shipping that somewhere with `zfs send`. No database dump, no maintenance mode, no dance to make sure the DB and the files agree with each other. That's the operational win I mentioned up top, and it's real.

You can skip all of this and let Docker use internal volumes. It works fine. But then your data lives somewhere in `/var/lib/docker/volumes/` and you're a lot less in control of it, so I do recommend the host path.

## Build Your .env File

```bash
cp .env.example .env
```

Now open `.env` in your editor. It's long, close to 500 lines, but it's mostly comments and about 90 percent of it doesn't apply to us. Here's what actually matters.

**Tell Compose which files to load:**

```bash
COMPOSE_FILE=docker-compose.yml:traefik/opencloud.yml
```

Core service plus Traefik, and notice `storage/decomposeds3.yml` is not in that list. That's how we get local storage.

Setting this in `.env` means you can just run `docker compose up -d` from here on out instead of typing `-f this -f that` every single time. Much nicer, and it makes the whole thing reproducible if you ever hand it to Ansible or a CI pipeline.

**Your domain:**

```bash
OC_DOMAIN=cloud.yourdomain.com
```

**Your admin password:**

```bash
INITIAL_ADMIN_PASSWORD=some-genuinely-strong-password
```

Read this bit carefully because it's a real gotcha. This variable is only read on the very first startup. Once OpenCloud initializes, changing it in `.env` does absolutely nothing. And if you start the stack with it blank, the container will just restart-loop and you'll have to wipe the config directory and start over. So set it now, before the first `up`.

After first boot, you change the admin password through the OpenCloud settings UI or the CLI, not from this file.

**Your storage paths:**

```bash
OC_CONFIG_DIR=/srv/opencloud/config
OC_DATA_DIR=/srv/opencloud/data
```

Use absolute paths here.

**Let's Encrypt:**

```bash
TRAEFIK_ACME_MAIL=you@yourdomain.com
TRAEFIK_SERVICES_TLS_CONFIG="tls.certresolver=letsencrypt"
```

That second one is already the default, but I like setting it explicitly so it's obvious what's going on when I read this file again in six months.

**And now the one that will actually bite you:**

```bash
INSECURE=false
```

Go find line 8 of your `.env`. It says `INSECURE=true` and it is not commented out. That's there so the local development setup with self-signed certs works out of the box, which is reasonable enough, but on an internet-facing server you need to flip it. The README's config table claims the default is `false`, and in the compose file it technically is, but the shipped `.env.example` overrides that. Change it.

**A couple more worth setting:**

```bash
DEMO_USERS=false
TRAEFIK_DASHBOARD=false
```

The demo users are `alan`, `mary`, `margaret`, `dennis`, and `lynn`, all with the password `demo`, all publicly documented. On a box reachable from the internet, that is not something you want. It defaults to false, but go confirm it anyway.

## Test Certificates Against Staging First

I know, you want to just start the thing. Give me thirty seconds, this'll save you a headache.

Let's Encrypt rate limits are strict and they count failures. If your DNS is subtly wrong, or a firewall rule is quietly blocking port 80, you can burn through your attempts and get locked out on that domain for hours. So we test against the staging server first, which has effectively no limits.

In `.env`:

```bash
TRAEFIK_ACME_CASERVER=https://acme-staging-v02.api.letsencrypt.org/directory
```

Then bring it up:

```bash
docker compose up -d
docker compose logs -f traefik
```

Give it a minute, then hit `https://cloud.yourdomain.com` in a browser. You'll get a certificate warning, and that's expected. Click through it, look at the certificate details, and check the issuer. If it says something like "Fake LE Intermediate X1" or "(STAGING) Let's Encrypt", the whole ACME flow worked. Beautiful. Your DNS is right, your ports are open, Traefik is doing its job.

Now go get real certificates. Clear the variable:

```bash
TRAEFIK_ACME_CASERVER=
```

Then delete the staging certs so Traefik goes and fetches fresh ones:

```bash
docker compose down
rm -f certs/acme.json
docker compose up -d
```

Quick note on that file. `certs/acme.json` is where Traefik stores your certificates and its ACME account key. It lives in the repo's `certs/` directory, which is gitignored, and it persists across restarts. Back it up with everything else, or at minimum know that deleting it means re-issuing, which counts against your rate limit.

Give it another minute and reload. Green padlock, real cert, no warning. And there we go.

## Log In

Head to `https://cloud.yourdomain.com`.

- Username: `admin`
- Password: whatever you set in `INITIAL_ADMIN_PASSWORD`

And just like that, we're in.

First thing you'll notice is Spaces, which is OpenCloud's organizing concept and honestly one of my favorite things about it. Instead of "here's your home folder, now share individual directories out of it," you create project spaces with their own membership and quota. It maps to how people actually work together a lot better than folder sharing does, and it's the one area where I think OpenCloud is straightforwardly ahead of Nextcloud's model.

Poke around, upload something, make a space. Then confirm it's writing where you expect:

```bash
sudo ls -la /srv/opencloud/data
```

You should see the storage tree filling in. Would you look at that. Files on disk, no database anywhere in sight.

## Watch the Logs on First Run

Even when everything works, tail the logs once so you know what healthy looks like:

```bash
docker compose logs -f opencloud
```

The first run does `opencloud init`, which generates all the internal service secrets and writes them into your config directory. On every start after that, the command fails harmlessly because the config already exists, and the entrypoint ignores the error and starts the server anyway.

So if you see an init error scroll by on restart number two, that's normal and by design. It threw me the first time.

## Optional Extras

The base install is files, sharing, and search. Here's what else you can stack on, roughly in the order I'd add it.

### Collabora for Document Editing

If you want to open a `.docx` in the browser and actually edit it, you need Collabora. Add a DNS A record for `collabora.yourdomain.com` pointing at the same IP, then update `.env`:

```bash
COMPOSE_FILE=docker-compose.yml:weboffice/collabora.yml:traefik/opencloud.yml:traefik/collabora.yml
COLLABORA_DOMAIN=collabora.yourdomain.com
```

Then find these two lines and deal with them:

```bash
COLLABORA_SSL_ENABLE=false
COLLABORA_SSL_VERIFICATION=false
```

`COLLABORA_SSL_ENABLE=false` is correct for our setup, because Traefik is terminating TLS and talking plain HTTP to Collabora on the internal network. But `COLLABORA_SSL_VERIFICATION=false` should be commented out on an internet-facing server so Collabora actually verifies the certs it talks to.

```bash
docker compose up -d
```

One thing that changed recently and confused a lot of people, myself included: the WOPI server used to be its own container on a `wopiserver.*` subdomain. It now runs inside the main OpenCloud process and gets served on your main domain under `/wopi` and `/collaboration`. So there's no extra DNS record for it, and if you're following an older tutorial that tells you to make one, just ignore that part.

Do note that Collabora and Euro Office are mutually exclusive. They both use the same WOPI service, so pick one.

### Full Text Search with Tika

By default, search covers filenames. If you want to search inside your PDFs and documents, add Apache Tika:

```bash
COMPOSE_FILE=docker-compose.yml:search/tika.yml:traefik/opencloud.yml
```

It's off by default for performance reasons and that's a fair default, since Tika extracts and indexes content on upload and that costs CPU. The base `apache/tika:latest` image is around 300MB and handles PDFs, Office docs, and text just fine. There's a `latest-full` variant at about 1.2GB if you need OCR, set with `TIKA_IMAGE=apache/tika:latest-full`, but most people won't.

### Radicale for Calendars and Contacts

This is the partial answer to that scope gap I mentioned earlier:

```bash
COMPOSE_FILE=docker-compose.yml:radicale/radicale.yml:traefik/opencloud.yml
```

Every authenticated OpenCloud user gets a personal calendar and address book over CalDAV and CardDAV, which you can point Thunderbird or your phone at. If you're setting a data directory for it, the same ownership rule applies:

```bash
sudo mkdir -p /srv/radicale && sudo chown -R 1000:1000 /srv/radicale
```

```bash
RADICALE_DATA_DIR=/srv/radicale
```

It's genuinely useful and I'm glad it's in there. It's also still not Nextcloud Calendar with shared team calendars and scheduling, so set your expectations accordingly.

### ClamAV Antivirus Scanning

If you're sharing upload links with people outside your household, scanning uploads is a reasonable idea:

```bash
COMPOSE_FILE=docker-compose.yml:antivirus/clamav.yml:traefik/opencloud.yml
START_ADDITIONAL_SERVICES="antivirus"
```

That second variable is really easy to miss, and without it the whole thing silently does nothing. If you're adding more than one extra service, comma separate them, like `notifications,antivirus`.

Heads up that ClamAV wants around 1GB of RAM for its signature database, which meaningfully changes the "runs great on low-power hardware" math. Worth it if you need it, skip it if you don't.

## If You Already Run a Reverse Proxy

Plenty of us already have nginx, Caddy, or Nginx Proxy Manager sitting on 80 and 443. In that case, skip Traefik entirely:

```bash
COMPOSE_FILE=docker-compose.yml:external-proxy/opencloud.yml
```

That exposes OpenCloud on port 9200 and you forward your domain to it from your existing proxy. Forward the whole domain, which covers the `/wopi` and `/collaboration` paths automatically.

One specific gotcha that will absolutely get you if you use Nginx Proxy Manager: do not enable "Block Common Exploits" on the proxy host. It breaks desktop client authentication with a 403, and there is nothing in the OpenCloud logs that will point you toward it.

## Backups, Which Is the Whole Point

Here's the payoff for setting it up with local storage.

Everything that matters lives in two directories:

- `/srv/opencloud/config` for the generated config and secrets
- `/srv/opencloud/data` for all files and metadata
- Plus `certs/acme.json` in the repo if you want to avoid re-issuing certificates

On ZFS:

```bash
sudo zfs snapshot tank/opencloud@$(date +%Y%m%d)
sudo zfs send -i tank/opencloud@previous tank/opencloud@$(date +%Y%m%d) | ssh backup-box zfs recv tank/backups/opencloud
```

Or just rsync it somewhere:

```bash
docker compose stop opencloud
sudo rsync -aAX /srv/opencloud/ /mnt/backup/opencloud/
docker compose start opencloud
```

You can snapshot live on ZFS, but stopping the container for a moment gives you a guaranteed clean state and it takes all of a few seconds.

Compare that to backing up Nextcloud, where you need the data directory, `config.php`, and a consistent `mysqldump` taken at the same logical moment, ideally with the instance in maintenance mode. Both are doable and both get scripted eventually. But one of them has a lot fewer ways to be subtly wrong six months later when you actually need the restore to work. That's not marketing copy, that's just what having no database gets you.

## Updating

```bash
cd opencloud-compose
git pull
docker compose pull
docker compose up -d
```

The compose file pins a specific version, currently 7.5.0, so `git pull` is what moves you forward. I like that as a default, since you're not going to get surprise-upgraded because a `latest` tag moved under you overnight.

Take a snapshot before you upgrade anyway. And read the release notes, because OpenCloud is moving quickly, and a fast-moving young project is exactly where you want to know what changed before you find out the hard way.

The nice part is there are no schema migrations to sit through. New container, same data directory, back up in seconds.

## Troubleshooting

### The Container Keeps Restarting

Ninety percent of the time it's one of two things. Either `INITIAL_ADMIN_PASSWORD` wasn't set before the first boot, or your data directories aren't owned by 1000:1000. Check `docker compose logs opencloud`, then check `ls -la /srv/opencloud`.

### Certificates Won't Issue

Confirm DNS resolves from outside your network, not just from the server itself. Confirm 80 and 443 are open at both the firewall and any cloud provider security group. Then read `docker compose logs traefik` and look for ACME errors. If you burned through your rate limit, that's a wait, not a fix.

### The Browser Says Not Secure Even Though Certs Issued

You probably still have `INSECURE=true` sitting in `.env`. Flip it and recreate the stack.

### The Desktop Client Can't Authenticate

If you're behind an external proxy, that's the Nginx Proxy Manager "Block Common Exploits" thing. Turn it off.

### Everything Looks Fine but Uploads Fail

Check disk space, then check permissions on the data directory again. It's almost always permissions.

General debugging:

```bash
docker compose ps
docker compose logs -f
docker compose logs -f opencloud
```

## Final Thoughts

I like it. More than I expected to, honestly.

The no-database thing is not a gimmick. It genuinely changes the operational shape of running this in a homelab. Spaces are a better sharing model than folder-based sharing. It's fast, it's light, and this compose repo is one of the cleaner modular setups I've worked with, which counts for a lot when you're the one maintaining it at midnight.

But I'm not moving off Nextcloud, and I want to be straight with you about why. I use Calendar, Contacts, and Deck constantly, Talk occasionally, and there's a handful of app store things I'd have to give up entirely. OpenCloud doesn't have those and isn't trying to. That's a legitimate design choice on their part, not a failing, but it means the answer for me personally is no for now.

Where I would genuinely recommend it: you want a Drive replacement, you don't need groupware, you're running modest hardware, and you want a backup story you can explain to someone in one sentence. That's a real category of person, and OpenCloud serves it better than Nextcloud does.

Where I'd say wait: you need polished mobile and desktop clients, you rely on third-party apps, or you need to be able to search a forum at 2am and find someone who already hit your exact error. Two years of project history against ten years is just a real gap.

I'm keeping this instance running alongside my Nextcloud box and I'll come back to it in a few releases. On-demand sync landing would be a big deal for me.

If you've been running OpenCloud for a while I'm really curious how it's gone, especially with the desktop clients, so let me know in the comments on the video. And if you've got a Nextcloud setup you love, I'm right there with you. With all that, I do hope this one was useful, and I hope you have an absolutely beautiful day.
