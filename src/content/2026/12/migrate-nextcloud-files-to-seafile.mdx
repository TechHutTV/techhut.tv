After I got Seafile up, I wanted to bring over a Nextcloud folder that was already sitting on an SMB share. My source was `ncdata/__groupfolders/1/files`, and I wanted those contents in a new **Archive** library with the same folder structure.

We'll run Seafile's Linux client inside the server VM, so your computer only has to drive the job over SSH. This copies files and folders. Nextcloud accounts, shares, permissions, comments, and version history stay behind.

## Before you start

This follows my [Seafile on Fedora and Unraid setup](/self-host-seafile-docker-unraid). The commands assume that VM's `/srv/seafile` project, the `/mnt/seafile` mount, and `seafile.service` are already there. Seafile should be working on its HTTPS address before you start the migration.

You'll also need an SMB account that can read the source folder, and enough space on the destination to keep both copies. The source has to expose ordinary, readable files. If Nextcloud encryption or some other storage backend is hiding the originals, export readable files through Nextcloud first.

Run the commands in the **Fedora VM over SSH**. Swap in your NAS address, share path, Seafile domain, and account names. The ownership examples use `1000:1000`. Use yours if they're different. I'm using `nano` to edit: **Ctrl+O**, **Enter** to save, then **Ctrl+X** to exit.

## How the files travel

![Files travel from the read-only NAS share through the Seafile client in Fedora, then through NPM and the gateway into a Seafile library on Unraid.](/docs-static/img/2026/12/migrate-nextcloud-files-to-seafile/cover.png)

Your laptop or desktop only drives the job over SSH. The files move between the NAS, the VM, and the reverse proxy. If the Seafile hostname points at NPM's LAN address, that traffic stays on the LAN. If you use a CDN or some other external proxy, check the VM's DNS and routing before you start a multi-terabyte transfer.

Seafile writes its own blocks on the destination share. You need room for the new library while the original files are still there, even when both shares live on the same NAS. The NAS is doing the source reads and the destination writes at the same time. Don't copy the source straight into Seafile's internal `seafile-data` directory.

## 1. Prepare an empty destination and a stable source

In Seafile's web interface, create an **empty, unencrypted library named Archive**. Leave it alone until the migration is finished and you've disconnected the client. This uses a sync client, so a change on either side can change what it tries to sync.

Stop editing the Nextcloud source during the copy, or use a read-only snapshot if your storage can make one. The read-only SMB mount stops this VM from writing. It does not stop Nextcloud, or another NAS client, from changing the original files.

In the examples below, replace `192.168.1.10`, the share/subfolder path, and `nasuser` with your values. Run everything in the **Seafile VM**.

```bash
sudo dnf install -y cifs-utils python3 python3-requests
sudo install -d -m 0750 /mnt/archive-source
sudo mount -t cifs //192.168.1.10/ncdata/__groupfolders/1/files \
  /mnt/archive-source \
  -o ro,username=nasuser,vers=3.1.1,uid=1000,gid=1000,nosuid,nodev,noexec,cache=strict
```

Enter the **SMB account's password** at the prompt. It stays out of the command and out of your shell history. The path includes the folder inside the share, so `files` itself won't become an extra folder inside Archive.

Check the mount and what's in it before you go further:

```bash
findmnt -T /mnt/archive-source -o TARGET,SOURCE,FSTYPE,OPTIONS
sudo ls -la /mnt/archive-source
```

You want the target `/mnt/archive-source`, filesystem `cifs`, and the `ro` option. The listing has to show the folders you want inside Archive. I caught a mount that showed the top of `ncdata` instead of the subfolder I meant. Checking here kept me from uploading the wrong tree.

## 2. Install the native Seafile client

Create private working folders on the VM's local disk for the client configuration, index, and temporary blocks:

```bash
sudo install -d -o 1000 -g 1000 -m 0700 /srv/seafile/migration
mkdir -p /srv/seafile/migration/tools /srv/seafile/migration/client
```

I used the official x86-64 CLI AppImage, version **9.0.21**, with Seafile Server 13.0.25. The client and server version numbers don't have to match. The [Seafile download page](https://www.seafile.com/en/download/) has the CLI package.

```bash
cd /srv/seafile/migration/tools
curl -fL --retry 3 \
  -o Seafile-cli-x86_64-9.0.21.AppImage \
  https://sos-ch-dk-2.exo.io/seafile-downloads/Seafile-cli-x86_64-9.0.21.AppImage
chmod 755 Seafile-cli-x86_64-9.0.21.AppImage
./Seafile-cli-x86_64-9.0.21.AppImage --appimage-extract
sudo mv squashfs-root /opt/seafile-cli-9.0.21
sudo chown -R root:root /opt/seafile-cli-9.0.21
sudo restorecon -RF /opt/seafile-cli-9.0.21
```

Extracting the AppImage lets systemd run the client without a FUSE mount. Putting the executable under `/opt` and restoring the normal Fedora labels also avoids the SELinux denial I hit when I tried to run it as a service from `/srv`. These install commands are for the first run. Don't drop another extraction on top of one that's already there.

Make a small shortcut so you don't have to repeat the client paths in every command:

```bash
sudo nano /usr/local/bin/seafile-migrate
```

```bash
#!/usr/bin/env bash
export APPDIR=/opt/seafile-cli-9.0.21
exec "$APPDIR/AppRun" "$@" -c /srv/seafile/migration/client-config
```

Install its permissions and initialize the isolated client:

```bash
sudo chmod 755 /usr/local/bin/seafile-migrate
sudo restorecon /usr/local/bin/seafile-migrate
sudo seafile-migrate init -d /srv/seafile/migration/client
```

Let `init` create `client-config`. Don't make that directory yourself first. The client keeps its index and temporary blocks under `/srv/seafile/migration`, and its working folder is the SMB source you already mounted. It doesn't need a second full copy staged on the VM, but the cache still needs free space.

### Leave room for the migration cache

My source had a single file around **47 GB**. The original 64 GB VM disk ran out of room once Fedora, the containers, and temporary blocks were all on it. I expanded the virtual disk to **128 GB**, then grew Fedora's partition, LVM volume, and filesystem so the guest could use the extra space.

Plan for your largest file, the other files getting prepared in the same batch, and free space for the server that's already running. A 128 GB disk worked for my source. It is not a promise for bigger files, or for a VM that already has more data on it. Check `df -h /` before you start. If you expand the VM disk, check it again after. Making the virtual disk bigger does not grow Fedora's filesystem by itself.

Keep these two directories on the **same local filesystem**:

```text
/srv/seafile/migration/client/seafile-data/tmpfiles
/srv/seafile/migration/client/seafile-data/storage/blocks
```

The client creates temporary chunks, then renames them into its block cache. I moved only `storage/blocks` to the NAS, those two directories landed on different filesystems, and I got `Invalid cross-device link` errors. Keeping both in their default local spot avoids that, and it cuts down extra NAS reads and writes. The index and config should stay local too. Permanent Seafile data still lives on Unraid.

If you need to change storage during a transfer, stop the client service first and keep its config, index, and both cache directories. After you grow the filesystem, start the same service to resume. An unfinished file may need to be indexed again. That is not the whole library starting over.

### Save a detailed source inventory

Write down the source folder's file count and logical size in your NAS or file manager so you can compare when the copy finishes. My source was **10,675 files totaling 4.58 TB**.

For a detailed record of paths, sizes, and modification times, [download the inventory script](/docs-static/files/2026/12/migrate-nextcloud-files-to-seafile/source-inventory.py). Save and run it on the VM:

```bash
cd /srv/seafile/migration
curl -fL -o source-inventory.py \
  https://techhut.tv/docs-static/files/2026/12/migrate-nextcloud-files-to-seafile/source-inventory.py
sudo python3 source-inventory.py
```

It reads file metadata and doesn't touch the source. It writes `source-manifest.jsonl` and `source-inventory.json` in this working directory. If it reports an unreadable path or some other error, fix that before you copy anything.

### Check files the client may exclude

The client has [built-in exclusions](https://github.com/haiwen/seafile/blob/master/daemon/repo-mgr.c), including `.DS_Store`, `Thumbs.db`, and, by default, `*.tmp`. A library can also have a [`seafile-ignore.txt` file](https://help.seafile.com/syncing_client/excluding_files/) with more patterns. An excluded file can sit on the source and never show up as a sync error.

In my migration, **27 files totaling 3.29 GB** got left out: 26 Finder or Windows thumbnail files, and one video ending in `.mov.tmp`. I looked at the missing paths and decided to leave those out. Don't assume every file that looks temporary is junk. Check it before you accept a difference in the totals. Keep the original inventory, and write down any exclusions you decide to live with.

## 3. Run the client in the background with systemd

Create the service:

```bash
sudo nano /etc/systemd/system/seafile-archive-client.service
```

```ini
[Unit]
Description=Seafile client for Archive migration
After=network-online.target seafile.service mnt-archive\x2dsource.mount
Wants=network-online.target
RequiresMountsFor=/mnt/archive-source /mnt/seafile
BindsTo=mnt-archive\x2dsource.mount

[Service]
Type=simple
Environment=SEAFILE_SSL_CA_PATH=/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
Environment=APPDIR=/opt/seafile-cli-9.0.21
Environment=LD_LIBRARY_PATH=/opt/seafile-cli-9.0.21/usr/lib
ExecStartPre=/usr/bin/mountpoint -q /mnt/archive-source
ExecStart=/opt/seafile-cli-9.0.21/usr/bin/seaf-daemon -c /srv/seafile/migration/client-config -d /srv/seafile/migration/client/seafile-data -w /srv/seafile/migration/client/seafile
Restart=on-failure
RestartSec=15s
TimeoutStopSec=90
UMask=0077
Nice=5
```

Keep the literal `\x2d` in that mount-unit name. That's how systemd escapes the hyphen in `archive-source`. The mount dependency stops the client if systemd sees that source mount disappear.

The certificate-bundle path is for this Fedora installation. Check it exists, then start the service:

```bash
test -r /etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
sudo systemctl daemon-reload
sudo systemctl start seafile-archive-client.service
sudo systemctl status seafile-archive-client.service --no-pager
sudo seafile-migrate config -k delete_confirm_threshold -v 1
```

If the `test` command fails, find your distro's trusted CA bundle before you continue. Seafile documents `SEAFILE_SSL_CA_PATH` in its [Linux client installation notes](https://help.seafile.com/syncing_client/install_linux_client/). This fixed a certificate-path issue on my VM, and HTTPS verification stayed on.

The low deletion threshold adds a pause before it confirms a delete. It does not turn sync into an upload-only mode. You still want the empty destination, a source that isn't changing, the read-only mount, and the final disconnect. Use this systemd service to run the daemon. Don't also run `seaf-cli start`.

## 4. Connect the source to Archive

List your remote libraries using your Seafile domain and account email:

```bash
sudo seafile-migrate list-remote \
  -s https://seafile.example.com -u you@example.com
```

Enter your **Seafile account password** at the prompt. Find Archive and copy its library ID. Make sure you're grabbing the empty library you just created, then replace `YOUR_ARCHIVE_LIBRARY_ID` below:

```bash
sudo seafile-migrate sync \
  -l YOUR_ARCHIVE_LIBRARY_ID \
  -s https://seafile.example.com \
  -u you@example.com \
  -d /mnt/archive-source
```

The [native client's `sync` command](https://help.seafile.com/syncing_client/linux-cli/) connects an existing folder to a library. The first message can say it's starting a download while it grabs the remote library info. With an empty destination, it then indexes the source files and uploads them.

Once the job is running under systemd, you can drop the SSH session or turn your computer off. Leave the VM, NAS, and NPM running. This one-time source mount isn't in `/etc/fstab`, and the client service isn't enabled at boot. After a VM reboot, mount the SMB share again, check what's in it, and start the same service. Keep the client config so it can resume. Don't initialize it again.

## 5. Monitor progress

Check the client from any later SSH session:

```bash
sudo seafile-migrate status
sudo tail -n 30 /srv/seafile/migration/client-config/logs/seafile.log
df -h / /mnt/seafile
sudo du -sh /srv/seafile/migration/client
```

For a live view, run `sudo watch -n 10 seafile-migrate status`. Press **Ctrl+C** to close the view. The transfer keeps running.

`committing` means the client is indexing files. `uploading` means a batch is going out. **The percentage the client shows is not a reliable read on the whole migration.** Upload speed can drop to zero while more files get prepared, and the saved library size can sit still until an upload is committed.

Seafile's library info shows how much has landed in Archive. Compare that with your source folder's size if you want a rough sense of progress.

For a useful speed estimate, note the library's saved size, wait 30 to 60 minutes, and check it again. Divide the increase by the time that passed. That includes indexing and server processing, which a one-second upload reading leaves out. Use the same units for both readings. Decimal GB and binary GiB are not the same thing.

With both temporary-cache directories on my VM's local disk, I measured roughly **34-38 MiB/s overall**, around **130-143 GB per hour**, during the rest of the transfer. Moving the cache onto the Unraid array earlier in the migration dropped that to about **15-17 MiB/s**. Those numbers are from my setup, where the NAS was reading the source and writing the destination at the same time. Your disks, file sizes, and network will change the result.

Estimate the time left from the remaining bytes and that overall rate. Keep verification time separate, and stop stretching the estimate once the client is idle. A gap in the totals needs a look, not another countdown.

Watch local free space and NAS capacity. To pause the transfer if space gets low, or you need to do maintenance:

```bash
sudo systemctl stop seafile-archive-client.service
```

Start the same service to resume after you fix the issue and confirm both mounts. Don't delete its cache or config just to pause it.

Do note that this service doesn't pause itself when disk space gets low. Watch free space and stop it before the filesystem fills. Also read the client log even when `status` shows no errors. My cross-filesystem cache problem showed up in the log with no matching sync error in the status output.

## 6. Verify the copy, then disconnect the source

Wait for the client to report **`synchronized`**, with no active errors, and compare Archive's file count and logical size with the source folder or your saved inventory. Compare nested folders, including empty ones, and check file modification times. File count by itself isn't enough. A failed large file matters more than thousands of small ones that made it.

**`synchronized` does not mean every source file was copied.** If the totals differ, find the exact missing paths and check exclusions, source changes, and the client logs. Account for every difference before you call the migration done. For my copy, the destination had **10,648 files totaling 4.579 TB**. The 27 files I reviewed and left out explained the whole difference from the original inventory.

Download a handful of files from Archive: documents, images, and some larger files from different folders. Open them, and compare checksums against the originals where you can. For a downloaded test file that isn't sitting inside the source folder, use:

```bash
sha256sum /path/to/downloaded-test-file
sudo sha256sum /mnt/archive-source/path/to/original-file
```

The two hashes should match. Sampling is useful, but the only complete check is reading and comparing every file. Keep the original Nextcloud files until you're happy with verification and you have a separate backup of the new Seafile install.

Once you're good with verification, **disconnect sync while the source is still mounted**, then stop the client and unmount it:

```bash
sudo seafile-migrate desync -d /mnt/archive-source
sudo seafile-migrate list
```

Confirm Archive is no longer in the client's local library list before continuing:

```bash
sudo systemctl stop seafile-archive-client.service
sudo umount /mnt/archive-source
```

`desync` leaves the files in Seafile and on the NAS. It just removes the sync relationship. Archive is ready for normal use. This migration doesn't delete anything from Nextcloud.

## If the transfer gets stuck

| Symptom | First thing to check |
| --- | --- |
| The client reports a TLS error | Check `SEAFILE_SSL_CA_PATH` and the certificate chain. Keep certificate verification enabled. |
| The percentage resets or the saved total pauses | Check the client state and saved library size over time. Indexing and commit delays can leave the saved total unchanged temporarily. |
| `synchronized`, but the totals don't match | Compare missing paths with built-in exclusions and `seafile-ignore.txt`; investigate any remaining differences. |
| `No space left on device` | Stop the service and check local cache space as well as NAS capacity. Preserve client state before changing storage. |
| `Invalid cross-device link` or `failed to commit block` | Stop the service. Check that `tmpfiles` and `storage/blocks` are on the same filesystem. |
| The service fails with `203/EXEC` | Check the `/opt/seafile-cli-9.0.21` path, executable permissions, and Fedora SELinux labels. |

For service errors, run `sudo journalctl -u seafile-archive-client.service -n 80 --no-pager`. The client log is at `/srv/seafile/migration/client-config/logs/seafile.log`.

Before you trust the new library, include it in your [Seafile backup setup](/self-host-seafile-docker-unraid#a-quick-note-on-backups).

With all that, I do hope the copy lands clean. Have a great one.
